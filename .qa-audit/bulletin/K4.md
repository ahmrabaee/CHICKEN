# K4 bulletin (frontend architecture)

- [FOR:ALL] Backend error envelope is `{success:false, error:{code,message,messageAr}}`, but ~50 frontend call sites read `response.data.messageAr/message/code` (wrong level) → real backend Arabic errors are replaced by generic fallbacks ("حدث خطأ"), and `lib/api-errors.ts:getPostingErrorToast` (PERIOD_LOCKED/FREEZE_DATE/ALREADY_* toasts) NEVER matches. UI testers: don't trust the toast text as the backend reason; check network response.
- [FOR:ALL, UI/E2E, reports testers] VERIFIED: frontend default date ranges use `toISOString().slice(0,10)` on local dates → in Asia/Jerusalem/Gaza the "this month" range is (prev-month-last-day .. current-month-day-before-last). Affects Reports, Accounting PDFs, customer/supplier statements, default document dates after local midnight. Dashboard is NOT affected (date-fns). See findings/K4.md K4-007.
- [FOR:sales/tax testers] POS hard-codes a 15% tax estimate for ANY selected tax template (pages/POS.tsx:328) and sends the cash payment = that estimated total. With a template ≠ 15% expect backend CUSTOMER_REQUIRED/OVERPAYMENT or a tiny unintended receivable. K4-001.
- [FOR:sales/barcode testers] POS scale-barcode lines display the label total but the DTO only sends weightGrams+pricePerKg; backend recomputes. Label total (incl. tax) is never persisted. K4-002.
- [FOR:security/authz testers] Backend authz is NOT aligned with UI page gating: e.g. POST /wastage has no role/page guard (UI treats /wastage as admin-only); /reports/profit-loss and /reports/stock-vs-gl are allowed for accountant at the API while UI hides them; GET /debts/receivables and GET /debts/:id have no page-access guard; PageAccessGuard uses exact path match while UI uses prefix match. Tokens (access+refresh) live in localStorage and every request body (including login password) is console.logged by lib/axios.ts:42 and hooks/use-auth.ts:19.
- [FOR:UI/E2E] Frontend map + top-10 UI leads: knowledge/architecture-frontend.md §1 and §10. POS loads only the first 100 items (K4-021); payment form only the first 500 sales / 100 purchases (K4-012); purchase "pay full" can trip OVERPAYMENT through float vs per-line rounding (K4-013).
- [FOR:ALL] All ×/÷1000 factors left in the frontend are weight (g↔kg); no stale ×1000 money conversion was found. Frontend lib/scale-barcode.ts is dead code (only its tests use it); live parsing happens in backend /barcode/lookup.
