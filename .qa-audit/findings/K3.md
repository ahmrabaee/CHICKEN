# K3 Findings — Backend Architecture & Posting Map

Context: in `dev` and `baseline` profiles `gl_engine_enabled=false`, `tax_engine_enabled=false`, so the **legacy posting path**
(`AccountingService.createJournalEntryInternal`) is in effect. "(GL-engine path)" findings only bite if those flags are switched on.
Empirical scripts: `.qa-audit/tests/K3/posting-probe.mjs` (+ `posting-probe2.mjs`, `probe3.mjs`); outputs in
`.qa-audit/tests/K3/probe-output.txt`, `probe2-output.txt`. Instance `k3` (port 3192, fresh dev DB), run 2026-11-25.
Historical context checked: bulletin/K2.md (seed bypass, D-14 insufficient-balance guard, write-off, purchase hard delete).

### K3-001: Voiding a sale after a separately-recorded payment double-refunds cash and leaves phantom AR
- Status: VERIFIED
- Severity: Critical
- Area / files: app/backend/src/sales/sales.service.ts:711-855 (voidSale), payments/payments.service.ts:123-229, accounting/accounting.service.ts:553-660
- Test executed: yes — posting-probe.mjs. Credit sale 10000 to customer 1 -> POST /payments/sale 4000 cash -> POST /sales/7/void. Net GL delta: **cash −4000, AR +4000** (expected 0/0). customer.currentBalance = 0, debt written_off, PLE delinked — so the 4000 AR residue exists only in GL.
- Root cause: voidSale reverses each payment JE (DR 1120 / CR 1111) AND the void JE credits cash for `sale.amountPaid` (already including that payment) and AR only for `total − amountPaid`.
- Impact: every voided invoice that had a later payment overstates AR and understates cash by the payment amount; trial balance still balances so nobody notices.
- Recommendation: refund only once (either don't reverse payment JEs or exclude them from the void JE).

### K3-002: `POST /sales/:id/payments` (SalesService.addPayment) records money with NO journal entry
- Status: VERIFIED
- Severity: Critical
- Area / files: sales/sales.service.ts:861-957; route has no RolesGuard (any authenticated user).
- Test executed: yes — credit sale 10000 to customer 2, POST /sales/:id/payments 3000 cash -> 201; journal_entries for that payment = 0; GL cash Δ 0, AR Δ 0; debt amountPaid 3000 'partial'; customer.currentBalance 7000.
- Impact: subledger (debt, customer balance, PLE, sale.amountPaid) says paid, GL says unpaid; cash never enters GL; such a payment cannot be cancelled later (cancelPayment → JOURNAL_ENTRY_NOT_FOUND). Also no bankAccountId/branchId stored; sale read outside tx.
- Recommendation: one payment-posting service; remove or route this endpoint through PaymentsService.

### K3-005: Purchase numbering is COUNT-based + hard delete ⇒ purchase entry permanently blocked
- Status: VERIFIED
- Severity: Critical (blocks a core workflow in normal operation)
- Area / files: purchases.service.ts:1062-1065 (generatePurchaseNumber = count+1, outside tx), :894-923 (remove hard-deletes)
- Test executed: yes — created PUR-000005/6/7, DELETE /purchases/<PUR-000006> → 200; next POST /purchases → **409 DUPLICATE_ENTRY purchase_number**, retry → 409 again (and will keep failing: count+1 = 7 already exists).
- Same mechanism verified for lots: after that delete, POST /stock-transfer failed **409 DUPLICATE_ENTRY lot_number** (generateLotNumber = `LOT-<date>-count+1`, purchases.service.ts:1067, stock-transfer.service.ts generateLotNumber). Same-day lot creation (purchases, transfers) is blocked until midnight UTC changes the prefix.
- Also count-based: EXP- (expenses.service.ts:198), CN- (credit-note.service.ts:210), PAY- in sales.service.ts:979 and purchases.service.ts:548/579, GL-engine JE- (gl-entry.factory.ts:74). Expenses are hard-deletable too (K3-015) ⇒ same EXP- collision expected (SUSPECTED, not executed).

### K3-019: Manual JE reversal nests a second $transaction and creates an UNPOSTED reversal (legacy path)

### K3-025: Other notable code-level risks (SUSPECTED)
- JWT secret falls back to `'default-secret-change-me'` if JWT_SECRET missing (auth.module.ts:17, jwt.strategy.ts:16). Logout/password change do not invalidate already-issued 15-min access tokens (session token never checked).
- `DISCOUNTS_GIVEN` and `OPERATING_EXPENSES` both map to 5400 "Other Expenses" (accounting.service.ts:41-43), and 5400 is also the GL-engine round-off account; seeded 4900 "Sales Discounts" and 5200 group are unused. `ACCOUNT_CODES.BANK='1112'` is a group account.
- voidSale / addPayment / recordSalePayment / cancelPayment / creditNote.submit read the document before/outside the transaction (double void / overpayment races).
- Purchase create skips lines whose item is missing but still includes them in grandTotal; purchase `docstatus` stays 0 after creation (posted but "draft"); `receive` endpoint unreachable for API-created purchases (receivedAt always set) and would post a second JE without debt.
