### K4-001: POS tax estimate hard-coded at 15% regardless of selected tax template
- Status: SUSPECTED
- Severity: High
- Area / files: pages/POS.tsx:327-332, 409-414; backend app/backend/src/sales/sales.service.ts:356-385; app/backend/src/accounting/tax/tax-calculation.service.ts:34-74
- Test executed: no (code review only)
- Reproduction:
  1. Settings → Tax templates: create a sales template with rate 1600 bps (16%) (or multi-row / `actual` / on_previous_row template).
  2. POS: add 1 kg of an item priced 100.00, choose that template, sale type نقدي, leave "المبلغ المدفوع" empty (auto = full total) or type the shown total.
  3. Complete sale.
- Expected: the UI total equals what the backend will post; a "full cash" sale is fully paid.
- Actual (predicted): UI computes `estimatedTaxMinor = round(net * 1500 / 10000)` for ANY template; the cash payment sent = UI total (115.00) while backend grandTotal = 116.00 → remaining 1.00 > 1 minor → backend raises CUSTOMER_REQUIRED (walk-in) or silently books a 1.00 receivable on the selected customer. With a template < 15% the backend rejects OVERPAYMENT. Receipt preview/print also shows the wrong tax and total.
- Root cause: client-side duplicated tax calculation with a constant instead of the template's rows (backend supports on_net_total / on_previous_row_amount / on_previous_row_total / actual).
- Impact: cashier-facing total ≠ invoice total; phantom tiny debts or blocked sales; printed receipt misstates tax.
- Historical context checked: none yet (decision-log.md not yet available at time of writing).
- Recommendation: fetch template rows (or a backend "preview totals" endpoint) and compute with identical rounding, or print the receipt from the saved sale.

### K4-002: Scale-barcode line shows label total, but sale submits weight × system price (label total discarded)
- Status: SUSPECTED
- Severity: High
- Area / files: pages/POS.tsx:144-189 (addToCart barcodeTotal), 192-212, 395-407 (DTO has only weightGrams + pricePerKg); backend app/backend/src/barcode/barcode.service.ts:127-156; app/backend/src/sales/sales.service.ts:330
- Test executed: no
- Reproduction:
  1. Enable custom barcode (14-digit template: start '2', 6-digit item code, 7-digit total incl. tax).
  2. Scan a label where the scale's price/kg differs from item.defaultSalePrice, or where total/price is not an exact multiple (e.g. total 1001, price/kg 3000 → inferred weight 0.334 kg → backend line = round(0.334*3000)=1002).
  3. Compare cart line total vs saved sale line total.
- Expected: invoice line equals the label total the customer saw (or the UI warns).
- Actual (predicted): cart shows label total (`total = barcodeTotal`), backend recomputes `round(weightGrams/1000 * pricePerKg)` — differs by rounding (≥1 minor) or by the full difference when the scale price differs from system price. Label "TotalPriceWithTax" is treated as net, so if a tax template is also selected tax is charged twice.
- Also: when barcode lookup falls back to static barcode, weight defaults to 1 kg.
- Recommendation: send the barcode total (or line amount) to the backend, or display the recomputed amount; define whether label totals include tax.

### K4-007: Default report/statement date ranges shifted one day back in the shop's timezone (UTC+2/+3)
- Status: VERIFIED (logic reproduced in Node under TZ=Asia/Jerusalem / Asia/Gaza; dev machine TZ = "West Bank Standard Time")
- Severity: High
- Area / files: pages/Reports.tsx:63-71 (getDefaultDateRange), 170-182 (presets incl. year), 197 (stock-vs-GL asOf); components/reports/PdfPreviewDialog.tsx:57-66; pages/Accounting.tsx:415-417 (income statement / balance / trial PDF params); pages/Customers.tsx:107-108, pages/customers/CustomerProfile.tsx:605-606, pages/Suppliers.tsx:83-84, pages/suppliers/SupplierProfile.tsx:639-640 (statements); components/accounting/AccountLedgerDialog.tsx:33; default "today" in forms: PaymentProfile.tsx:421, ExpenseProfile.tsx:294, PurchaseProfile.tsx:97, JournalEntryProfile.tsx:94
- Test executed: yes — `.qa-audit/tests/K4/tz-date-range.mjs`
  - TZ=Asia/Jerusalem, now 2026-11-24 10:00 → monthStart "2026-10-31", monthEnd "2026-11-29", yearStart "2025-12-31"
  - TZ=Asia/Gaza, now 2026-11-24 01:30 → today "2026-11-23"
  - TZ=UTC → "2026-11-01" / "2026-11-30" / "2026-01-01" (correct)
- Reproduction: open التقارير → المبيعات (default "this month") on a machine in Palestine/Israel time; inspect request params.
- Expected: local calendar month 1..30 (business requirement: period reports by local day).
- Actual: `new Date(y, m, 1).toISOString().slice(0,10)` converts local midnight to UTC → previous day. Monthly reports/P&L/VAT/statements by default include the last day of the previous month and EXCLUDE the last day of the current month; "year" preset starts 31 Dec of prior year; balance-sheet/trial "asOf" and default document dates (payment/expense/purchase/journal entry) are YESTERDAY between 00:00 and 02:59/03:59 local.
- Root cause: UTC serialization of local dates. (The Dashboard uses date-fns `format()` and is correct — inconsistent pattern.)
- Impact: VAT report and P&L for "this month" misstate the period (one day shifted); documents entered just after midnight get yesterday's date (wrong period, possibly into a locked period → PERIOD_LOCKED).
- Recommendation: use local formatting (date-fns `format(d,'yyyy-MM-dd')`) everywhere; backend testers should also check how backend interprets date-only bounds (UTC vs local).
