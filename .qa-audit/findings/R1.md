## 2. New findings (sales-return feature and new code)

### R1-001: Voiding a sale after returns reverses the whole sale again (double refund, phantom stock)
- Status: VERIFIED | Severity: Critical
- Area: `sales/sales.service.ts` voidSale (~711) vs returnSale (~897); no link between them
- Test: `tests/R1/06-returns.mjs` R1, R3
- Reproduction: cash sale 4 kg@50 (20000, cost 8000); return all 4 kg resellable (cash 20000); void the sale.
- Expected: void blocked (or reverses only the unreturned part).
- Actual: void OK. Stock 10 kg -> 14 kg (4 kg that never existed twice), cash -20000 twice, revenue 4110 reversed twice (net GL since return: 1111 -40000, 1131 +16000, 4110 +40000, 5100 -16000). Return rows are not marked on the sale (totals unchanged, GET /sales/:id has no returns field).
- Impact: every returned then voided invoice costs the shop its full price again and inflates stock.
- Root cause: returns live only in stock_movements/JE; void checks only `isVoided`.
- Recommendation: record returned qty/amount on the sale lines; block or net the void; refuse return after void (this half works: SALE_VOIDED).

### R1-002: Concurrent returns bypass the over-return guard
- Status: VERIFIED | Severity: Critical
- Area: returnSale reads prior returns before the transaction (`alreadyReturned` built outside `$transaction`)
- Test: 06 R11
- Reproduction: 4 parallel full returns (4 kg each) of one 4 kg sale.
- Actual: 4 x OK; inventory 22 kg (bought 10, sold 4, "returned" 16), cash -80000 on a 20000 sale. Return + damaged return + void in parallel: all OK, inventory 13 kg, movements 16000 vs inventory 13000.
- Recommendation: re-check inside the transaction against a persisted returned quantity with a conditional update; idempotency key.

### R1-003: Return on a discounted sale refunds more than the customer paid
- Status: VERIFIED | Severity: High
- Area: returnSale uses `saleLine.lineTotalAmount` (ignores header discount); JE never reverses 4900
- Test: 06 R7; 07 (engines ON)
- Actual: sale 20000 - header discount 2000 = 18000 paid; full return refunds 20000 (+2000 loss, 4900 discount debit remains). Engines ON, taxed 15% + discount 1000, 4 kg: paid 21850; returns 1 kg + 3 kg refund 5750 + 17250 = 23000 (+1150).
- Impact: any discounted sale returned gives money away.
- Recommendation: allocate header discount and tax on actual invoice totals, reverse discount proportionally, cap refund at amount paid.

### R1-004: Cash refund on an unpaid credit sale pays out money never received and leaves the debt
- Status: VERIFIED | Severity: High
- Test: 06 R4
- Actual: credit sale 20000 unpaid; return 1 kg with refundMethod cash: cash -5000, customer balance still 20000, debt open 20000; customer then pays the full 20000 (accepted) for goods of which 5000 worth is back in stock. A second return with credit refund moves debt to paid 5000 / balance 15000 while sale row stays unpaid/amountPaid 0. refundMethod credit on a walk-in sale silently becomes a cash refund.
- Recommendation: refund method derived from payment state; refund cannot exceed amount paid; reduce debt for unpaid part.

### R1-010: Cart with the same item on several lines is falsely rejected when stock spans lots

### R1-014: max+1 numbering is string-ordered and limited to the GL-engine/sale paths
- Status: SUSPECTED (code review; not executed) | Severity: Low
- Area: `gl-entry.factory.ts:74-85` (orderBy entryNumber desc, parseInt of digits); `sales.service.ts:1132` (4-digit pad, string order)
- Reasoning: a number with another prefix (e.g. `JE-SEED-0003`, as `PUR-SEED-0003` exists for purchases: `max purchase_number` returned PUR-SEED-0003 in 02) sorts above `JE-0…` and yields a low next number, colliding forever; sale number SAL-date-9999 sorts above SAL-date-10000, so the 10001st sale of a day would collide. My DB's JE numbers all use the JE- prefix, so not triggered.
