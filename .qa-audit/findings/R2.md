## New findings

### R2-001: Backups taken under concurrent writes are silently corrupt (WAL mode + copyFile of the main db file)
- Status: VERIFIED
- Severity: Critical (backup is the only recovery path; archives marked `success` but unusable / internally inconsistent)
- Area / files: `app/backend/src/modules/backup/backup.service.ts:256-272`, `utils/sqlite-snapshot.ts:16-37` (plain `fs.copyFile` of `app.db`), `prisma/prisma.service.ts` (WAL enabled by C-1)
- Test executed: yes - `tests/R2/backup-under-writes.mjs` (5 writers, 20 backups, each archive extracted and `pragma integrity_check` + sale/journal consistency), `tests/R2/bk-w.mjs` (W=1 and W=3). Outputs `backup-under-writes.out.txt`.
- Reproduction: start instance; run N writers posting cash sales; call `POST /system/backup` every ~1.2 s; extract `db/app.db` from each archive.
- Actual: W=5: 3 of 20 not usable: `wrong # of entries in index audit_logs_user_id_idx` with 4 unbalanced journal entries; another with 39 sales lacking journal entries; W=1: `row 5017 missing from index audit_logs_user_id_idx`; W=3: 7/20 including `database disk image is malformed`, `row 28362 missing from index journal_entry_lines_cost_center_id_idx`. All runs report `status=success`. T6-11 (old code, 3 writers, 9 backups) and my first run of the same script on the new code (9 backups) were all clean, so the failure appears only with sustained write load (ratio rises with writers).
- Root cause: with WAL on, `PRAGMA wal_checkpoint(TRUNCATE)` runs on one pooled connection and then the main file is byte-copied while other connections keep committing and auto-checkpointing into the same file. The copy is not a SQLite-consistent snapshot (needs `VACUUM INTO` / backup API / copy under a read transaction). The new global audit interceptor adds one more INSERT per mutating request, so there is more write traffic during the copy.
- Impact: a restore of such an archive gives a database with missing index rows / orphan documents; nobody is told, the run is "success", retention may then delete the good older backups.
- Historical context: QA-003/QA-004 only covered restore validation and overwrite; the WAL change (C-1) introduced this. Claim in `DB_CONCURRENCY_LOCKING.md` says WAL + backup compatible; not tested under load there.
- Recommendation: use `VACUUM INTO`/online backup, verify `integrity_check` on the produced snapshot before marking success.

### R2-002: Restore while the API is serving requests leaves Prisma permanently disconnected (needs process restart)
- Status: VERIFIED
- Severity: High
- Area / files: `backup.service.ts:552-570` (`$disconnect` ... `reconnectPrismaWithRetry`)
- Test executed: yes - `backup-under-writes.mjs` last step: restore backup id while 5 writers run.
- Actual: `POST /system/backups/:id/restore` -> 500 after 5.7 s (`Invalid this.prisma.systemSetting.upsert() ... Engine is not yet connected`); afterwards `GET /sales` -> 500, `POST /auth/login` -> 500 (even for a fresh client), writers 1,530 x 500. Only a process restart recovers (after restart integrity ok, journal_mode wal, data = the restored backup, 5,005 sales). Idle restore (T6-10 rerun) is fine: 201 in 51 ms and the app keeps working.
- Root cause: requests arriving between `$disconnect()` and reconnect trigger Prisma's lazy auto-connect, racing the explicit reconnect; no maintenance mode / request gate. Likely pre-existing (not WAL specific) but never exercised under traffic in the first audit; restore is exposed to the accountant (QA-002) so a low-privilege user can trigger it at the busiest moment.
- Recommendation: maintenance gate that rejects/queues requests during restore; restart the process after restore.

### R2-003: Audit interceptor drops rows under load, truncates bodies into invalid JSON, logs successes only
- Status: VERIFIED
- Severity: Medium
- Area / files: `app/backend/src/common/interceptors/audit.interceptor.ts` (`tap` after handler; `.catch(() => {})`; `.slice(0, 4000)`)
- Test executed: yes - `audit-under-load.mjs`: 5 concurrent writers 20 s -> 1,046 sales, 1,043 `sales/create` audit rows (3 silently lost); 120-line sale -> audit `changes` length 4000, `JSON.parse` fails. `audit-coverage.mjs`: 400/403/404 attempts leave no row (cannot see who tried to void/forge); `PUT /settings/*` and others log only the first path segment (`entityType=company` for `/settings/company`, `templates` for `/tax/templates`, `accounting` for `/accounting/journal-entries`, `action=sale` for `POST /payments/sale`) so filtering by entity is inconsistent; manual rows from the older service-level audit remain (void, return, adjustment appear twice, the service row has NULL IP/branch).
- Business impact: the audit trail is not append-reliable (silent loss), and forensic value of a truncated body is limited; failed/forbidden attempts invisible.

### R2-004: Restoring an archive made without WAL silently switches the live database back to rollback-journal mode
- Status: VERIFIED
- Severity: Medium
- Area / files: `prisma.service.ts` (pragmas only at `onModuleInit`), `backup.service.ts` restore (file swap)
- Test executed: yes - `tests/R2/restore-nonwal.mjs` (`restore-nonwal.out.txt`): live `journal_mode wal` -> import a tar.gz holding the golden (pre-WAL) `db/app.db` -> restore 201 -> file header now `delete`, app keeps running without WAL until next process restart (busy_timeout/synchronous also only applied once per boot, on a single pooled connection).
- Impact: C-1 protection (WAL) disappears after any restore of an older backup; the concurrency behaviour the owner was promised changes silently.
- Recommendation: re-apply pragmas after reconnect; ideally restart the process after restore.

### R2-006: Sales return refunds the gross amount, ignoring the sale discount
- Status: VERIFIED; Severity: High
- Area / files: `sales.service.ts returnSale`, `accounting.service.ts createSaleReturnJournalEntry`
- Test executed: yes - `returns.mjs` scenario A: 2 kg @ 30.00 = 60.00, header discount 6.00, customer paid 54.00. Return of the whole 2 kg, refund cash: response `refundGross 6000`; GL delta `1111 -6000`, `4110 +6000` (Dr), `1131 +4800`, `5100 -4800`; the 4900 discount (600) is not reversed.
- Impact: every return from a discounted sale pays the customer the discount back in cash (6.00 here) and understates net revenue; sell at a discount then return = free cash.
- Recommendation: refund the net amount actually paid in proportion to returned lines and reverse the 4900 share.

### R2-007: Concurrent returns of the same line all succeed; cash refund allowed on an unpaid credit sale
