### T2-001: Stock adjustments never touch lots, so already-written-off grams are later sold at FIFO cost (or real stock can't be sold)
- Status: VERIFIED (confirms and extends K3-009)
- Severity: Critical
- Area / files: app/backend/src/inventory/inventory.service.ts:227-419 (createAdjustment); :437-476 (allocateFIFO reads lots only)
- Test executed: yes — tests/T2/t02-adjust.mjs → t02-adjust.out.txt
- Reproduction and numbers:
  - A: buy 10 kg @20.00 and 10 kg @30.00; sell 5 kg (COGS 10,000); adjust −5 kg → value out = 40,000×5/15 = **13,333** at weighted average (FIFO would be 5 kg@20 = 10,000). Lots keep 15 kg. Sell 10 kg → FIFO takes 5@20 + 5@30 = 25,000. End state: **inventory 0 g / value 16.67 ₪ (1,667)**, **lots 5 kg / 150.00 ₪** (phantom lot), GL 1131 = 1,667. The 5 kg phantom lot cannot be sold (inventory check) but appears in the lot lists, the transfer source-lot picker and the wastage lot picker.
  - B: buy 10 kg @20; adjust +5 kg **without unitCost** → inventory 15 kg/30,000, JE Dr 1131 10,000, **no lot**. Selling 15 kg → `400 INSUFFICIENT_STOCK "Short by 5000g"` although the screen shows 15 kg. After selling 10 kg: inventory 5 kg/100.00 ₪, lots 0 → 5 kg can never be sold.
  - D: buy 10 kg @20, sell 3 kg, adjust −7 kg to **zero** (JE 14,000 loss), adjust +5 kg @25.00 (new LOT-ADJ lot, JE 12,500), sell 5 kg → FIFO takes the **written-off** lot @20 (COGS 10,000, not 12,500). End: inventory 0 g/2,500, lots 7 kg/16,500.
  - E: decrease with `lotId` → that lot is NOT decremented (lot 10 kg, inventory 8 kg). A `lotId` belonging to a DIFFERENT item is accepted (201).
- Expected (PRD2 6.4, BP06 §8, I-14/I-15/I-16, K1 §3 oracle: FIFO per lot): decrease consumes lots FIFO (or the chosen lot) at lot cost; increase without cost must create a lot (or be rejected); Σlots = inventory = GL.
- Actual: three representations drift: per item drift after one scenario each: A +5 kg/+13,333; B −5 kg/−10,000; D +7 kg/+14,000; E +3 kg/+6,000 (lots − inventory).
- Root cause: adjustment works only on the `inventory` aggregate (weighted average) — D-03 mixed design; lot table is the FIFO source for sales.
- Impact: physical counts (the shop's routine correction) corrupt FIFO: COGS of following sales is wrong, written-off meat is "resold" at its old cost, and stock that the screen shows cannot be sold at POS. Every count adjustment grows the gap between lots and the GL.
- Recommendation: make adjustments lot-aware (decrease FIFO/selected lot at lot cost; increase always creates a lot at a required cost); add an invariant check Σlots = inventory.

### T2-002: Adjustment increase with unitCost 0 or NEGATIVE is accepted; inventory value changes with NO JE and NO SLE
- Status: VERIFIED
- Severity: High
- Area / files: inventory/dto/inventory.dto.ts:78-82 (`unitCost` only `@IsInt`, no `@Min`); inventory.service.ts:289-291 (value uses dto.unitCost), :294 (lot only if >0), :388 (JE/SLE only if addedValue>0)
- Test executed: yes — t02-adjust.mjs scenario C
- Reproduction: item with 10 kg @20.00 (value 20,000). `POST /inventory/adjustments {increase, 10000 g, unitCost: 0}` → 201, qty 20 kg, value 20,000, avg ₪10.00, no lot/JE/SLE. Then `{increase, 10000 g, unitCost: -1500}` → 201, qty **30 kg, value 5,000 (avg ₪1.67/kg)**, no JE, no SLE, no lot.
- Expected: unitCost > 0 required (D-05 requires cost); every adjustment hits GL (I-26).
- Actual: inventory.total_value reduced by 15,000 silently. In the run, Σinventory.total_value of test items = 33,167 while GL 1131 = 48,167 (gap 15,000 = this one call). `/reports/stock-vs-gl` still shows difference **0** (see T2-004).
- Impact: an accountant with `/inventory/adjustments` page access can write inventory value up/down off-book; displayed average cost becomes absurd.
- Recommendation: `@Min(1)` on unitCost for increases; reject zero-value increases or require explicit cost.

### T2-004: Stock-vs-GL reconciliation report cannot detect any inventory drift (compares SLE to GL only)
- Status: VERIFIED
- Severity: High
- Area / files: app/backend/src/inventory/stock-ledger/stock-reconciliation.service.ts:37-160
- Test executed: yes — t02-adjust.mjs (end of run): `/reports/stock-vs-gl` summary `{totalStockValue 48167, totalAccountValue 48167, totalDifference 0}` while Σlot value ≠ Σinventory.total_value ≠ GL (per-item drifts in T2-001, 15,000 off-book in T2-002).
- Expected (BP06 §9, I-14): reconciliation of GL stock vs physical valuation (Σ lot remaining × cost / inventory valuation).
- Actual: report only sums SLE.stock_value_difference vs GL lines per voucher; SLE is written by the same code that writes the JE, so it is equal by construction except for vouchers lacking one side (wastage, transfer). Lots and the inventory table are never consulted. Also `asOfDate=YYYY-MM-DD` means midnight UTC (excludes the day itself); `isReversed:false` filter hides reversed JEs while their SLE remain.
- Impact: the one report meant to prove inventory = GL gives a false "0 difference".
- Recommendation: add Σlots and Σinventory.total_value columns per item; flag differences.

### T2-005: Stock transfer (cutting) creates/destroys inventory value with no JE; destination cost is free input (incl. 0 and same-item revaluation)
- Status: VERIFIED (confirms K2-005 / K3-016 / K1-003; refines: transfer status ends `completed`, NOT `draft`)
- Severity: Critical
- Area / files: app/backend/src/stock-transfer/stock-transfer.service.ts:133-360 (no AccountingService call; dest lot cost = `line.unitCost`; source reduced at source lot cost); DTO `unitCost @Min(0)`; frontend default cost = item.defaultPurchasePrice ?? defaultSalePrice (StockTransferProfile.tsx:63, per K2)
- Test executed: yes — tests/T2/t03-transfer.mjs → t03-transfer.out.txt
- Reproduction / numbers (raw chicken item 1):
  1. Buy 10 kg raw @18.00 (GL 1131 +18,000). Transfer 9 kg → breast 4 kg @28.00 + thigh 3 kg @22.00 + wing 2 kg @20.00 (the UI default costs). Source value consumed **16,200**, destination lots **21,800** → **+5,600 created**; GL delta **{}** (no JE). Selling the 4 kg breast then books COGS 11,200 for meat whose share of the bird cost was 7,200.
  2. Breast 2 kg → skewer @0 → **−5,600 destroyed** (skewer lot 2 kg value 0; later sales have COGS 0).
  3. Breast 3 kg → **breast** (same item) @99.99 → **+21,597**: anyone with transfer access can revalue stock arbitrarily.
  - End of script: Σinventory.total_value = Σlot value = SLE = **93,294**, GL 1131 = **66,300** → **26,994** unbooked. `/reports/stock-vs-gl` does show this (transfer rows accountValue 0).
- Expected (I-23, WST 4.3, API-04, STOCK_TRANSFER_FIX_PLAN §6.2): Σdestination value = source value consumed; inventory GL unchanged; no P&L effect.
- Impact: inventory and COGS/gross profit misstated on every cutting operation (the shop's daily core process); because default costs are item reference prices, the error is systematic. GL 1131 can go negative when inflated lots are sold.
- Historical context: D-04 (defaultPurchasePrice must never enter valuation) violated; D-25 deliberate per-line cost → INTENTIONAL-BUT-RISKY at best.
- Recommendation: compute destination costs server-side from source value (allow only relative weighting), reject same-item transfers.

### T2-006: Cutting has no yield/bone-loss concept; un-transferred loss stays in the source lot at full cost; batch date not preserved; expiry ignores product shelf life
- Status: VERIFIED
- Severity: High
- Area / files: stock-transfer.service.ts:147 (source reduced only by Σline weights), :165-167 (expiry = dto, else source expiry, else **now+7 days**), :212 (`receivedAt: new Date()`)
- Test executed: yes — t03-transfer.mjs T1/T2
- Numbers: 10 kg raw → 9 kg cuts leaves 1 kg (value 1,800) in the raw lot that physically no longer exists; to model "10 kg → 7 kg parts" the user must type 25.71/kg AND separately waste the 3 kg leftover, which then expenses another 5,400 (double count of the loss). Source lot without expiry → cut products expire at **now + 7 days** although category "قطع دجاج طازجة" shelf life is 2 days. Destination lots get `receivedAt = now` (FIFO moves cut stock behind later purchases; FPRD "preserve original batch date" not met, C-17).

- Impact: phantom raw stock after every cutting; fresh parts sellable up to 7 days with no expiry warning.
