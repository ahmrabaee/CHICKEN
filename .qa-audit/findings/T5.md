## New findings

### T5-001: Unauthenticated full-database download via forgeable backup token (hardcoded secret absent from .env template)
- Status: VERIFIED
- Severity: Critical
- Area / files: `modules/backup/security/backup-token.service.ts:19` (`BACKUP_DOWNLOAD_SECRET` default `'fallback-secret-change-in-env'`), `backup.controller.ts:147` (`@Public() GET /system/backups/:id/download`); `.env` and `.env.example` contain NO `BACKUP_DOWNLOAD_SECRET`.
- Test executed: yes — `tests/T5/backup-exfil.mjs` (`backup-exfil.out.txt`).
- Reproduction: (1) a backup exists (auto-cron or any admin/accountant trigger). (2) Attacker forges `base64url(payload).HMAC-SHA256(payload, 'fallback-secret-change-in-env')` for `{backupId, exp}`. (3) `GET /v1/system/backups/<id>/download?token=<forged>` with NO auth header → **200, application/gzip, 35839 bytes (gzip 1f8b)** = the entire SQLite DB. Control with a wrong secret → 401.
- Root cause: signing secret falls back to a constant published in source; the env var is never set (missing from the deploy template), so the fallback is the live key. Download endpoint is `@Public()` by design (token-gated) but the token gate is defeated.
- Impact: anyone who can reach the API (per PRD it is internet-exposed behind Caddy for remote owner access) downloads the full database — all customers, suppliers, prices, costs, financials, and every user's bcrypt password hash — with no credentials. Backup ids are small integers (brute-forceable).
- Recommendation: fail boot if `BACKUP_DOWNLOAD_SECRET` unset; add it to `.env.example`; require an authenticated admin for download.

### T5-002: Entire backup/restore/import module is unauthorized for non-admins → full data takeover by an accountant
- Status: VERIFIED
- Severity: Critical
- Area / files: `modules/backup/backup.controller.ts` — `@Roles('admin')` on handlers but the controller has NO `@UseGuards(RolesGuard)` and `RolesGuard` is not global (`app.module.ts:95` registers only `JwtAuthGuard`).
- Test executed: yes — `authz-matrix.csv`, `backup-exfil.mjs`, `input-attacks.mjs`, `guard-gap-writes.mjs`.
- Reproduction (as accountant `t5acc`): `GET /system/backups` → 200 (lists all); `POST /system/backups/:id/download-link` → 201 (mints an official signed link); `PUT /system/backup/config {path_vps}` → 200 and **persisted** (controls backup storage path); `POST /system/backups/import` (multipart .tar.gz) → **201, archive imported**; `POST /system/backups/:id/restore` passes the guard (404 only for a missing id).
- Impact: a cashier/accountant can exfiltrate every backup, **import and restore an arbitrary database** (wiping/replacing all data — e.g. zeroing their own debt, creating admin users, forging history), and redirect where backups are written. Full compromise of a financially sensitive system from the lowest role.
- Recommendation: add `@UseGuards(JwtAuthGuard, RolesGuard)` to the backup controller (and every `@Roles` controller lacking it — see T5-009); restrict restore/import to admin with confirmation + audit.

### T5-003: JWT secret fallback enables admin-token forgery; access tokens are never revocable
- Status: VERIFIED
- Severity: Critical (conditional on `.env` presence) / High (revocation)
- Area / files: `auth/auth.module.ts:17`, `auth/strategies/jwt.strategy.ts:16` (`JWT_SECRET` default `'default-secret-change-me'`); `jwt.strategy.validate` re-derives identity from `payload.sub` only.
- Test executed: yes — `forge-default-proof.mjs`, `jwt-forgery.mjs`.
- Reproduction: run server with `JWT_SECRET` unset (fallback active) → forge `HS256({sub:1,type:'access'}, 'default-secret-change-me')` → `GET /users/me` 200 as admin. On THIS build `backend/.env` is loaded by absolute path so the fallback is masked (forgery with default secret → 401), but a deploy that forgets `.env` is wide open. Any party that learns the signing secret mints admin tokens without a password (verified against `t5a` using its known harness secret → 200 admin).
- Impact: token forgery = full admin impersonation; the per-request DB check only enforces `isActive`, not the token's secret source.
- Recommendation: remove both hardcoded fallbacks; fail fast when `JWT_SECRET`/`BACKUP_DOWNLOAD_SECRET` are missing or weak.

### T5-004: Accountant/cashier can read all cost, profit, supplier prices, expenses and financial reports (PRD forbids)
- Status: VERIFIED
- Severity: High
- Area / files: `reports/reports.controller.ts` (`@Roles('admin','accountant')` on profit-loss, stock-vs-gl, expenses), `sales/sales.controller.ts` (no role filter; response carries `totalCost/totalProfit`), `purchases.controller.ts:48` (`GET /purchases/:id` allows accountant). The `accountant` role's `permissions` JSON lacks `reports.financial`, but no guard enforces permissions (K3-024) — only coarse role is checked.
- Test executed: yes — `deep-checks.mjs §B`.
- Reproduction (as accountant): `GET /reports/profit-loss` → 200 `{netProfit:20000, costOfGoodsSold, grossMargin}`; `GET /reports/stock-vs-gl` 200; `GET /reports/expenses` 200; `GET /purchases/1` 200 (supplier + cost); `GET /sales/1` exposes `totalCost`,`totalProfit`,`cost`; `GET /reports/dashboard` exposes receivables/payables.
- Impact: the business requirement that only the owner sees margins/costs/supplier pricing is enforced only by hiding UI pages; the API hands all of it to any accountant/cashier token (or a forged/borrowed one). Confidential pricing and profitability leak to staff.
- Recommendation: enforce `reports.financial`/`costVisibility` at the API (permission guard), strip cost/profit fields from sale responses for non-privileged roles.

### T5-005: Logout and password change do not invalidate live access tokens; refresh tokens are replayable (no rotation)
- Status: VERIFIED
- Severity: High
- Area / files: `auth/auth.service.ts` logout/changePassword clear `refreshToken` + `currentSessionToken` but `jwt.strategy` never checks `currentSessionToken`; `refreshToken()` issues a new access token without rotating the refresh token.
- Test executed: yes — `deep-checks.mjs §C`.
- Reproduction: login → `POST /auth/logout` → old **access** token still `GET /users/me` 200 (refresh → 401). Change password → old access token still 200 (refresh → 401). `POST /auth/refresh` twice with the SAME refresh token → both 200 (replayable for 7 days).
- Impact: a stolen access token (tokens live in `localStorage` and every request/response incl. login password is `console.log`ed — K4-010; receipt XSS can read them — K4-005) remains valid up to 15 min after the victim logs out or resets a compromised password; a stolen refresh token mints access tokens for 7 days and cannot be "used up". No way to force-logout a user.
- Recommendation: check `currentSessionToken`/a token version per request; rotate refresh tokens on use and detect reuse.

### T5-006: No brute-force protection, account lockout, or login rate limiting; client IP never recorded
- Status: VERIFIED
- Severity: High (system is internet-exposed per PRD/DEPLOYMENT.md)
- Area / files: `auth/auth.service.ts` validateUser/login (no attempt counter/lockout); `createAuditLog` hardcodes `ipAddress:'localhost'`.
- Test executed: yes — `input-attacks.mjs`.
- Reproduction: 10 consecutive wrong passwords for `admin` → 10×401, then correct password → 200 (never locked). Audit rows show `ip_address='localhost'` for every login.
- Impact: unlimited online password guessing against a remotely reachable admin login (weak policy below makes this worse); forensic logs cannot show the source of a breach because the real IP is discarded.
- Recommendation: add lockout/backoff + rate limiting (e.g. `@nestjs/throttler`) on `/auth/login` and `/auth/refresh`; record the real client IP.

### T5-007: Weak password policy (8 chars, no complexity) — PRD requires a strong policy
- Status: VERIFIED
- Severity: Medium
- Area / files: `auth/dto/auth.dto.ts` and `users/dto/*` use only `@MinLength(8)`; no uppercase/digit/symbol/denylist.
- Test executed: yes — `input-attacks.mjs`: passwords `"password"`, `"12345678"`, `"aaaaaaaa"` all accepted (201); `<8` rejected.
- Impact: trivially guessable admin/cashier passwords, compounding T5-006.
- Recommendation: enforce length ≥12 + complexity + common-password denylist on setup, create, change, and admin reset.

### T5-008: Audit log does not cover user management, backups, settings, page-access or tax changes
- Status: VERIFIED
- Severity: Medium (High for a financial/multi-user system)
- Area / files: `users.service.ts`, `modules/backup/backup.service.ts`, `settings.service.ts`, `page-access.service.ts`, `accounting/tax/tax-template.service.ts` contain **no** audit writes; only auth (login/logout/change-password) and some financial ops (sales void, payments, debts) log.
- Test executed: yes — after a full session of user creates/deactivate, page-access edits, backup create/import, config writes, tax create/delete, `audit_logs` on `t5a` held only `login/logout/update` rows.
- Impact: "who created/deactivated a user, who restored or imported a database, who changed settings or a tax rate, who granted themselves page access" is unrecorded — the exact actions in T5-001/002/009 leave no trail. With the unauthenticated restore/import (T5-002) an attacker can also replace the DB (and its audit table) wholesale.
- Recommendation: audit all privileged mutations with real actor + IP; consider append-only/off-box audit storage.

### T5-009: Role guard missing on many controllers → unauthorized writes by accountant / any user
- Status: VERIFIED
- Severity: Medium (several individually High)
- Area / files: controllers with `@Roles` but no `RolesGuard`: backup (T5-002), `accounting/tax/tax-template.controller.ts` (also uses an inline body type, not a class DTO → no whitelist), `accounting/reconciliation/reconciliation.controller.ts`, `accounting/credit-note/credit-note.controller.ts`, `accounting/chart-of-accounts/account.controller.ts`. Controllers with no role restriction at all: `sales` (except void), `wastage`, `inventory` GETs, `debts/receivables|:id`.
- Test executed: yes — `guard-gap-writes.mjs`: accountant created a tax template (rate 9900 bps) and deleted it (201/200); reconciliation apply, credit-notes, wastage create, and `POST /sales` (even as a page-revoked accountant) all pass auth (400 validation, not 403).
- Impact: a cashier/accountant can edit tax rates (mis-stating VAT), allocate payments (PLE), issue credit notes, record wastage (stock + GL), and create sales regardless of page access — none gated.
- Recommendation: apply `RolesGuard` on every `@Roles` controller; add explicit role/page gates to sales/wastage; replace inline body types with validated DTOs.

### T5-010: Swagger UI and JSON served unauthenticated with no environment guard
- Status: VERIFIED
- Severity: Medium
- Area / files: `main.ts` sets up `/api/docs` and the OpenAPI doc unconditionally (no `NODE_ENV` check, no auth).
- Test executed: yes — `GET /api/docs` and `/api/docs-json` → 200 with no token.
- Impact: full API surface (187 endpoints, schemas, the backup/restore routes) is disclosed to anyone reaching the server in production, aiding the attacks above.
- Recommendation: disable Swagger in production or gate it behind admin auth.

### T5-011: Deactivation, privilege-escalation, injection and pollution defenses — VERIFIED SECURE (documented)
- Status: VERIFIED (negative results — these are safe)
- Severity: Info
- Evidence (`deep-checks.mjs`, `input-attacks.mjs`): deactivated user's pre-issued access token AND refresh token both → 401 (strategy re-checks `isActive` each request). Accountant blocked (403) from creating admin users, editing/patching other users, resetting admin password, and granting itself page access. Mass assignment via `PUT /users/me` (`roleId/isActive/username/passwordHash` injected) → 400/ignored, roles unchanged (controller explicitly whitelists fields + global `forbidNonWhitelisted`). SQL injection via search/sort params → parameterized (Prisma), 200/400, never a SQL 500. Prototype pollution via `__proto__` body → global not polluted. `completeSetup` cannot be re-run after setup (`SETUP_ALREADY_COMPLETE`). Request body-size limit enforced (413 "request entity too large"). 500 responses do not leak stack traces/paths.

### T5-012: Second-order / deployment observations
- Status: VERIFIED (code/config)
- Severity: Low / Info
- CORS allowlist (`main.ts`) is strict (only `localhost:1420/5173`, `tauri://localhost`); a disallowed `Origin` gets no `Access-Control-Allow-Origin` (verified). Implication: the PRD "owner accesses from home" via a **browser** on the public domain would be CORS-blocked — remote access only works from the Tauri desktop app (`tauri://localhost`). Not a vulnerability, but confirm intended access path.
- `http-exception.filter.ts:71-76` returns the raw Prisma validation `exception.message` to the client (minor schema/info leak on malformed queries).
- node-tar extraction uses `strict:true` (mitigates classic `..` tar-slip), but the installed `tar` version is the one flagged critical for hardlink path traversal (T5-013) — reachable through restore/import (T5-002).

### T5-013: Dependency vulnerability triage (runtime-reachable)
- Status: VERIFIED
- Severity: Medium (triage of ORCH-006)
- Area / files: `npm audit` output saved at `tests/T5/npm-audit.json` (run in `sandbox/backend`, node_modules junctioned; no `audit fix` run).
- Runtime-reachable (keep): **tar** (critical, hardlink file overwrite) — backup create/restore/import; **multer** (high, DoS incomplete cleanup) + **body-parser** (high, size-limit bypass) + **path-to-regexp** (high, ReDoS) + **proxy-addr** (critical) — HTTP/upload path; **pdfmake** (high, SSRF) — every PDF (invoice/statement/report). Depends on whether user-controlled URLs reach pdfmake (templates appear to use local assets — lower exploitability, still patch).
- Dev/build-only (NOT in the running server): vitest, tinypool, vite, rollup, postcss, source-map-js, browserslist, @nestjs/cli, prisma/@prisma/config CLI, nanoid(dev), js-yaml(cli).
- Recommendation: prioritize upgrading tar, multer, body-parser/express, path-to-regexp, pdfmake; re-audit.
