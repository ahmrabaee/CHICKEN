### T6-001: Burst of concurrent POS sales → most requests fail with HTTP 500 DATABASE_ERROR after ~6 s (P1008 socket timeout / P2028 expired transaction)
- Status: VERIFIED
- Severity: High
- Area / files: app/backend/src/sales/sales.service.ts:283-660 (create: interactive `$transaction`, default 5 s timeout) + inventory/inventory.service.ts:423-476 (`allocateFIFO` → `getAvailableLots` uses `this.prisma`, i.e. a SECOND connection, while the sale tx holds a lock); prisma/prisma.service.ts (no busy_timeout / WAL / tx timeout tuning); common filter maps Prisma errors to 500 `DATABASE_ERROR`.
- Test executed: yes — `tests/T6/02-concurrency-threshold.mjs` (outputs `02-run1.out.txt`, `02-run2.out.txt`), `tests/T6/01b-oversell-race-partial.mjs`.
  - N = 1…15 parallel 10 g cash sales: all 201, sequentialised (~30 ms each, N=15 wall 663 ms).
  - N = 20: **8×201, 12×500** (run 2: 5×201, 15×500); N = 30: 13×201, 17×500. Every failing request hangs ~6 s.
  - 01b: 20 parallel 100 g sales on an item with 1000 g left → 6×201, **14×500** (expected 10 OK + 10 INSUFFICIENT_STOCK).
  - Backend log (`logs/t6.log`): `Prisma error P1008: Socket timeout (the database failed to respond …)` ×N and `P2028 Transaction already closed … timeout was 5000 ms, however 5724 ms passed`.
  - Invariants after each burst: clean (rollback is complete — no half-written sale; GL/count deltas = exactly the successful sales).
- Expected: valid sales either succeed or get a business error (4xx); DB contention handled by waiting/retrying (PRD: 3 concurrent users, unreliable network ⇒ retries create bursts).
- Actual: once enough transactions queue up, SQLite's rollback-journal lock + the out-of-transaction FIFO read on another pool connection produce a lock wait (tx A holds RESERVED/PENDING waiting for EXCLUSIVE; tx B's `allocateFIFO` read on a different connection is blocked by A's PENDING lock while B keeps its SHARED lock) that only breaks by the 5 s busy/tx timeout. The client receives a generic 500 with no retry hint.
- Impact: with 3 tills the threshold is not reached in normal clicking, but a reconnect storm (client retries after a network glitch, several tabs, batch imports, report generation in parallel) yields 500s for legitimate sales after a 6 s freeze; the cashier does not know whether the sale was recorded (it was not) → re-entry / double sale risk (see T6-00x idempotency).
- Root cause: reads that belong to the transaction are done on `this.prisma` (other connection) + journal_mode=delete + 5 s default interactive-tx timeout; P1008/P2028 not retried.
- Historical context checked: decision-log F-05 (sale_number P2002 retry ×5 — only handles P2002, not P1008/P2028); architecture-backend §3.1/§3.3.
- Recommendation: do all reads through `tx`; enable WAL + busy_timeout; consider `BEGIN IMMEDIATE`/a per-process write mutex; map P1008/P2028 to 503 + retryable code.

### T6-002: Stock adjustments lose updates under concurrency — inventory quantity overwritten with a stale absolute value (also erases concurrent SALES' decrements) while every request still posts its GL entry
- Status: VERIFIED
- Severity: Critical
- Area / files: app/backend/src/inventory/inventory.service.ts:227-262 (item + inventory read with `this.prisma` BEFORE the tx), :313-327 (`tx.inventory.upsert` writes `currentQuantityGrams: newQty, totalValue: newTotalValue` as absolute values computed from the stale read), :362-405 (SLE + JE posted per request regardless).
- Test executed: yes — `tests/T6/03-adjustment-lost-update.mjs` → `03-adjustment-lost-update.out.txt`
  - A) 5 parallel `POST /inventory/adjustments {itemId:3, decrease, 1000 g}` → 5×201, every response says `50000->49000`. Inventory 50000→**49000 g** (expected 45000), total_value dropped 28.00 while **GL 1131 credited 140.00** (5 JEs), 5 adjustment_out movements = −5000 g.
  - B) 5 parallel 500 g cash sales + 5 parallel 500 g decrease adjustments on item 2 → 10×201. inventory qty 50000→**49000** (expected 45000: **4000 g drift**), lots 47500 (sales decremented lots; adjustments don't touch lots — K3-009), SLE −5000 g, GL inventory −90.00, inventory_value −18.00. The sales' own `decrement` updates were overwritten by the adjustments' stale absolute write.
- Expected: I-18/I-15/I-26 — each adjustment removes its quantity exactly once; stock, lots, SLE and GL agree; concurrent sales never "undone".
- Actual: classic read-modify-write lost update; three representations of stock diverge (inventory table, lots, SLE/GL). Inventory table becomes higher than reality → the in-tx stock check of later sales trusts a phantom 4 kg.
- Impact: with only two users (cashier selling while the manager records a spoilage/count adjustment) the system silently "restores" sold kilograms in the inventory table; valuation, low-stock and stock-vs-GL reports diverge with no error. Repeated double-click on the adjustment dialog does the same (2 JEs, 1 qty change).
- Historical context checked: architecture-backend §3.1 (flagged as lost-update risk, now confirmed); K3-009 (adjustments don't touch lots); 75b3211 (WAVG fix after adjustment) — does not address concurrency.
- Recommendation: read inventory inside the tx and use relative `increment/decrement`; lock per item; idempotency key on the dialog.

### T6-003: Concurrent void of the same sale is executed N times — stock restored N×, N reversal JEs, AR/revenue/COGS reversed N×
- Status: VERIFIED
- Severity: Critical
- Area / files: app/backend/src/sales/sales.service.ts:711-735 (`voidSale`: sale + `isVoided` read with `this.prisma` BEFORE `$transaction`; no conditional update `where: {id, isVoided:false}` inside the tx)
- Test executed: yes — `tests/T6/04-void-pay-races.mjs` (a) → `04-void-pay-races.out.txt`
  - Credit sale SAL-20261125-0107 (2 kg, total 56.00, cost 44.00) → 5 parallel `POST /sales/112/void` (two sessions) → **5×200**.
  - inventory + lots of item 4 **+10000 g** (expected +2000; 8 kg phantom stock), 5 `sale_void` JEs (JE-000118…122), GL: AR −280.00, revenue 4110 Dr 280.00, COGS −220.00, inventory +220.00 (each 5× the sale). customers.current_balance −280.00 while open debts/PLE moved −56.00 → customer shows a 224.00 CREDIT the shop never owed.
  - T1 checker afterwards: AR-01/AR-02/INV-01..04 FAIL.
- Expected: I-06 "no double reversal", I-42 void nets to zero. Second void → 400 ALREADY_VOIDED.
- Actual: the ALREADY_VOIDED check is a pre-transaction read; SQLite serialises the 5 transactions but each re-runs the full reversal.
- Impact: a double-click on "إلغاء" (the button has only `disabled={isPending}`, K4-006) or a network retry by the admin silently creates stock and wipes receivables; P&L loses revenue/COGS N-1 extra times. - Recommendation: inside the tx `updateMany({where:{id, isVoided:false}, data:{isVoided:true}})` and abort if count = 0; unique (sourceType, sourceId) on reversal JEs.

### T6-004: Overpayment guard is outside the transaction — concurrent payments overpay an invoice by any amount; `/sales/:id/payments` additionally loses `sale.amountPaid` updates
- Status: VERIFIED
- Severity: Critical
- Area / files: app/backend/src/payments/payments.service.ts:123-148 (recordSalePayment: sale read + `amount > amountDue` check before `$transaction`); app/backend/src/sales/sales.service.ts:861-957 (addPayment: same pre-tx check and writes `amountPaid: sale.amountPaid + dto.amount` as an absolute stale value; no JE — K3-002).
- Test executed: yes — `tests/T6/04-void-pay-races.mjs` (b, c)
  - b) credit sale total 56.00 → 5 parallel `POST /payments/sale {amount 40.00}` → **5×201**: 200.00 accepted, **overpaid 144.00**; sale.amount_paid 200.00 status still "partial"; debt amount_paid 200.00 > total 56.00; customer 2 balance −144.00; GL cash +200, AR −200 (AR goes credit).
  - c) same via `POST /sales/:id/payments` → **5×201**, overpaid 144.00; **sale.amount_paid = 40.00** (lost update: 4 of 5 writes overwritten) while debt.amount_paid = 200.00, customer balance −144.00 more, PLE −200.00, **GL unchanged** (no JE). ### T6-005: No idempotency for document creation — a retried/double-submitted POST /sales creates a second complete sale
- Status: VERIFIED
- Severity: High
- Area / files: app/backend/src/sales/sales.controller.ts:72 (no idempotency key handling; `PreventDoubleSubmitGuard` in common/guards/prevent-double-submit.guard.ts is never used — K3 arch §JournalEntry); frontend services/sales.service.ts:50 (no key, K4-006).

### T6-013: Backup/restore integrity — positives and residual risks
- Status: VERIFIED (positives) / SUSPECTED (residuals)
- Severity: Medium
- Verified OK (`tests/T6/10-backup-restore.mjs`, `11-backup-under-load.mjs`, `14-kill-restart.mjs`):
  - backup → 3 sales + expense → restore: every table identical to the backup state (row-count + content hash, excluding `backup.*` settings), live app keeps working with the pre-restore JWT; restore takes ~60 ms.
  - 7 backups taken while 3 writers posted 1158 sales: every archive `integrity_check ok`, no sale without JE/lines, no orphan JE.
  - hard kill (TerminateProcess) during 3 parallel writers: integrity ok, no partial documents, checker shows no new failure; one purchase committed but never acknowledged to the client (ghost, cf. T6-007).
- Residual risks (code): restore copies over the DB file while other requests are in flight (they fail during the window; no maintenance mode); `ASSET_DIRS` are resolved against the backend install dir (`app/backend/data/uploads|assets`, `public/logos`) — not per DATABASE_URL — and restore `rm -rf`s them before copying from the archive, so an archive carrying `assets/*` overwrites files of whatever install runs it (not executed: forbidden dir for QA); the snapshot is a plain `copyFile` of a journal_mode=delete DB without holding a read lock (a commit during the copy could tear pages — not observed in 8 tries); each restore leaves a full plaintext `app.db.before-restore-*.bak` next to the DB forever (7 after this session); backups are unencrypted (PRD 10.4 asks encrypted/off-site); upload is buffered in memory (no size limit seen).
- Note: restore legitimately discards documents created after the backup (3 sales / 1 expense in the test) and sale numbers are reused (SAL-20261125-0133 issued twice in reality) — UI should warn and log this.

### T6-014: Cross-validation notes (concurrency leads)
- K3-008 "concurrent POS sales race → oversell": **NOT REPRODUCED** — 10×1 kg and 20×100 g against the last 1000 g: 0 g oversold (`01-oversell-race.out.txt`, `01b-…`).
