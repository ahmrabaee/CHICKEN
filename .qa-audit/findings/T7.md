## Findings

### T7-001: Payment form white-screens the entire app when "بطاقة"/"تحويل بنكي" is chosen and no bank account exists (ORCH-002 CONFIRMED)
- Status: VERIFIED
- Severity: High
- Area / files: app/frontend/src/pages/payments/PaymentProfile.tsx:845 (`<Link>` not imported); no React error boundary in the app
- Test executed: yes — `tests/T7/orch002.mjs` → `orch002.out.txt`; screenshots `shots/orch002-card.png`, `shots/orch002-transfer.png`
- Reproduction: dev profile (0 rows in bank_accounts — the state of every fresh install until the admin adds a bank) → login admin → /payments/new → طريقة الدفع = بطاقة (or تحويل بنكي).
- Expected: hint "add a bank account in Settings" rendered (that is what line 845 tries to render).
- Actual: `ReferenceError: Link is not defined`; React unmounts the whole tree → completely blank page (document body innerText length 0, sidebar gone). Only a reload recovers; entered data is lost.
- Root cause: missing import; build does not type-check (ORCH-001); no error boundary anywhere, so any render error blanks the whole application.
- Impact: on a fresh install a cashier/accountant cannot even see why card/transfer is unavailable; the app appears to crash during a financial entry.
- Historical context: ORCH-001/002.
- Recommendation: import Link; add a top-level ErrorBoundary; add `tsc --noEmit` to build.

### T7-002: POS with any tax template ≠ 15% — sale blocked with a misleading reason, rejected as overpayment, or a phantom receivable is booked (K4-001 CONFIRMED live)
- Status: VERIFIED
- Severity: High
- Area / files: app/frontend/src/pages/POS.tsx:327-332 (`estimatedTaxMinor = round(net*1500/10000)`); backend sales.service tax via template rows
- Test executed: yes — `tests/T7/pos1.mjs` → `pos1.out.txt` (scenarios B, C, D); screenshots `shots/pos1-B_*.png`, `pos1-C_*`, `pos1-D_*`
- Reproduction (UI, admin, dev profile): create sales templates "VAT 16% QA" (1600 bps) and "VAT 10% QA" (1000 bps) → POS → 1 kg صدور دجاج (35.00) → select template → POS shows الإجمالي 40.25 for BOTH templates → type 40.25 in المبلغ المدفوع → إتمام البيع.
- Actual:
  - 16 %, walk-in: POST /sales → 400 `CUSTOMER_REQUIRED`; toast "الدفع الآجل أو الجزئي يتطلب تحديد بيانات الزبون" although the cashier entered exactly the full total shown on screen.
  - 16 %, with customer name/phone: sale SAL-…-0002 saved with totalAmount 4060, amountPaid 4025, paymentStatus **partial**; GL: Dr 1111 40.25 + Dr 1120 0.35; debt DEB-SAL-…-0002 0.35 created and customer currentBalance 35 — the customer is told it is paid in full but owes 0.35. The UI toast is just "تم إنشاء الفاتورة بنجاح" (no hint that the invoice is partial).
  - 10 %: POST → 400 `OVERPAYMENT` ("المبلغ المدفوع أكبر من الإجمالي") when the cashier pays the displayed total; the only way to complete is to guess the real total (38.50) which the screen never shows.
  - 15 % (seeded template): UI 42.92 = backend 4292 (consistent for this template only).
- Expected: displayed total = backend total for whatever template is selected.
- Impact: any shop whose VAT is not exactly 15 % (Israel 18 %, PA 16 %) cannot sell with tax from the POS without errors / unintended debts; receipts misstate tax.
- Side observation (backend, for T3/T1): with tax_engine disabled, the 16 % and 15 % sales post the tax inside revenue 4110 (Cr 4110 4060 / 4292; no VAT payable 2120 line; sale_tax_breakdowns empty). See bulletin.
- Recommendation: compute totals with the template rows (or a backend preview endpoint); show backend totals after save.

### T7-003: Walk-in cash sale paid 0.01 short is accepted without a customer → 1-agora receivable with no owner
- Status: VERIFIED
- Severity: Low (amount tiny, but it breaks the AR control ↔ subledger invariant on every occurrence)
- Area / files: POS.tsx:338-341 (`isExplicitUnderPayment` uses tolerance 1 minor); backend sales.service customer check `remaining > 1`
- Test executed: yes — `tests/T7/pos1.mjs` scenario I

### T7-005: Double-click / double-Enter on "إتمام البيع" creates duplicate sales (K4-006 CONFIRMED)
- Status: VERIFIED
- Severity: High
- Area / files: POS.tsx:347-352, 932-936 (only guard is `disabled={createSale.isPending}`, which is not yet re-rendered between two clicks in the same frame); no idempotency key; backend has no duplicate-request protection for POST /sales
- Test executed: yes — `tests/T7/pos2.mjs` → `pos2.out.txt` section "K4-006"; DB check `sales` ids 13–19
- Reproduction: POS → 1 kg فروج كامل → paid 22 → (a) Playwright `dblclick()` on إتمام البيع, (b) focus button + Enter, Enter, (c) three synchronous `click()`s.
- Actual: (a) 2 sales (SAL-…-0011, -0012), (b) 2 sales (-0013, -0014), (c) 3 sales (-0008/9/10) — each with its own JE, stock deduction and cash debit, created 23–33 ms apart. UI shows one success toast per request and clears the cart; the cashier sees nothing unusual.

### T7-006: POS "طباعة" executes HTML/JS from the customer name (token theft) and prints an unsaved, wrong receipt (K4-005 CONFIRMED)
- Status: VERIFIED
- Severity: High (security: stored/typed HTML runs in the app origin with access to localStorage tokens; Tauri CSP is null)

### T7-013: Pasting/typing a number with a thousands separator saves a value 1000× too small (NumericInput turns "," into a decimal point)
- Status: VERIFIED
- Severity: High (silent misstatement of purchase cost / inventory value; same component is used in every money form)
- Area / files: app/frontend/src/lib/numbers.ts `normalizeToEnglishNumberString` (`str.replace(/[٫،,]/g, '.')` then joins extra dots); components/ui/numeric-input.tsx — used by Purchase, Payment, Expense, Credit-note, Journal entry, Reconciliation, Stock adjustment/transfer, Wastage, Customer/Supplier, Item, Settings forms
- Test executed: yes — `tests/T7/purchase.mjs` section "thousands separator"

- Actual: input shows "1.25000"; line total ₪2.50; PUR-000006 saved with pricePerKg 125 (1.25 ₪) instead of 125000 — no warning. Inventory lots get cost 1.25/kg (affects FIFO COGS later).
