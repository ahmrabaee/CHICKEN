# 🔐 الوحدة 4 — الصلاحيات والمحاسبون وحساباتهم

**الواجهة:** `/users` (المستخدمون) · `/settings` (الإعدادات) · السايدبار (إخفاء/إظهار حسب الصلاحية)
**الكود:** الباك إند `app/backend/src/users/`, `page-access/`, `auth/` · الواجهة `AppSidebar.tsx`, `ProtectedRoute`, `usePermissions`
**الأدوار المُهيّأة (seed):** `admin` و `accountant`.

---

## ⚠️ ملاحظة مهمة اكتُشفت من الكود
دور **"المحاسب" (accountant)** صلاحياته فعلياً **نقطة بيع/كاشير** وليست محاسبة:

```
ACCOUNTANT_PERMISSIONS = [
  dashboard.view,
  sales.create, sales.view, sales.discount.limited,
  purchases.view,
  inventory.view,
  wastage.create, wastage.view,
  customers.create, customers.view,
  debts.view, debts.collect,
  reports.sales
]
```

الوصف في الكود نفسه: *"POS operations with limited administrative access"*.

➡️ **المحاسب لا يملك:** `accounting.view` (شجرة المحاسبة/القيود)، التقارير المالية، المصروفات، المدفوعات، الموردين، المستخدمين، الإعدادات، سجل المراجعة.

**سؤال للمالك:** هل هذا مقصود (المحاسب = كاشير)، أم أن المطلوب أن يرى المحاسب القيود والتقارير المالية؟ هذا يحدّد إن كان خطأً يجب تصحيحه. (سيؤكّد الـ subagent المختص الوضع الأمني الفعلي.)

---

## 🧪 سيناريوهات الاختبار (من الواجهة)

### A) إنشاء مستخدم محاسب
1. كمدير: `/users` → إضافة مستخدم، أسند له دور **محاسب**، كلمة مرور ≥ 8 أحرف.
2. سجّل خروج، ثم دخول بالمستخدم الجديد.
3. **المتوقع:** يرى في السايدبار فقط العناصر المسموح بها (Dashboard, POS/Sales, Inventory عرض, Wastage, Customers, Debts, تقرير المبيعات).

**تحقق:**
- [ ] العناصر غير المصرّح بها **مخفية** من السايدبار.

### B) 🔴 اختبار تجاوز الصلاحيات عبر الـ API مباشرة (الأهم)
إخفاء العنصر من السايدبار **لا يكفي** — يجب أن يرفض الباك إند الطلب.
1. سجّل الدخول كمحاسب، خذ الـ token.
2. من المتصفح (DevTools) أو عبر `curl`، نفّذ طلباً لنقطة نهاية غير مصرّح بها، مثل:
   - إنشاء/تعديل حساب في شجرة المحاسبة (`POST /v1/accounting/...`).
   - إنشاء قيد يومية يدوي.
   - تعديل مستخدم آخر أو صلاحياته.
   - إبطال فاتورة بيع (`sales.void` ليست ضمن صلاحياته).
   - تعديل الإعدادات.
3. **المتوقع (آمن):** يرد الخادم **403 Forbidden**.
4. **إن رد 200/نجح ⟵ 🔴 ثغرة تصعيد صلاحيات حرجة.**

**تحقق:**
- [ ] كل نقطة نهاية حسّاسة محميّة بحارس صلاحيات (Guard) على الباك إند.
- [ ] لا توجد نقطة نهاية mutating بدون حماية.

### C) حدود المحاسب داخل الوظائف المسموحة
- [ ] الخصم: المحاسب محدود (`sales.discount.limited`) — تأكد أن الحد مُطبَّق فعلاً في الباك إند.
- [ ] تحصيل الديون: مسموح (`debts.collect`) — يعمل.
- [ ] عرض المخزون فقط: لا يستطيع التعديل/التسوية.

### D) إدارة حسابات المستخدمين
- [ ] إعادة تعيين كلمة مرور مستخدم (كمدير) تعمل.
- [ ] تعطيل/تفعيل مستخدم (`isActive`) يمنع/يسمح بالدخول.
- [ ] لا يمكن للمحاسب الوصول إلى `/users` إطلاقاً (FE + API).

### E) تطابق تعريفات الصلاحيات
- [ ] كل سلسلة صلاحية في `ADMIN_PERMISSIONS` / `ACCOUNTANT_PERMISSIONS` تطابق ما تفحصه الحُرّاس فعلاً (لا أخطاء إملائية تجعل صلاحية لا تُمنح أبداً).
- [ ] تعريفات الصفحات (`seedPageDefinitions`) متّسقة مع المسارات.

## 🔎 نتائج المراجع (اكتُشفت فعلاً)

### 🔴 الجذر: نموذج الصلاحيات التفصيلي **ديكوري بالكامل**
لا يوجد `PermissionsGuard` يقرأ مصفوفة `permissions` إطلاقاً (بحث شامل = صفر نتائج). الحماية الفعلية الوحيدة: الحارس العام `JwtAuthGuard` + حارس دور خشن `RolesGuard` (admin/accountant) **فقط حيث يُضاف يدوياً** + `PageAccessGuard`. كل سلاسل مثل `sales.void`, `debts.write_off`, `sales.discount.limited` **بيانات ميتة**. وحماية الواجهة **client-side فقط** (إخفاء بصري) ⟵ الـ API هو حدود الثقة الوحيدة وهو غير متّسق.

### ثغرات تصعيد صلاحيات فعلية (المحاسب عبر الـ API)
| الثغرة | المكان | الأثر |
|---|---|---|
| `@Roles('admin')` بلا `RolesGuard` ⟵ لا يُطبَّق | [tax-template.controller.ts:28](app/backend/src/accounting/tax/tax-template.controller.ts#L28) | المحاسب يُنشئ/يحذف قوالب ضريبة تتحكّم بالـ VAT/القيود |
| شطب ديون مسموح للمحاسب | [debts.controller.ts:96](app/backend/src/debts/debts.controller.ts#L96) | المحاسب يصفّي ذمم مدينة (مخفي في الواجهة، مفتوح في الـ API) |
| حد الخصم يفحص `discountPct` فقط | [sales.service.ts:262](app/backend/src/sales/sales.service.ts#L262) | المحاسب يرسل `discountAmount` ⟵ خصم غير محدود |
| إنشاء/ترحيل قيود يدوية للمحاسب | [accounting.controller.ts:115](app/backend/src/accounting/accounting.controller.ts#L115) | يناقض كون المحاسب بلا `accounting.*` |
| تقارير مالية (P&L/VAT/stock-vs-GL) | [reports.controller.ts:11](app/backend/src/reports/reports.controller.ts#L11) | كشف مالي كامل للمحاسب |
| `wastage` بلا أي حارس (JWT فقط) | [wastage.controller.ts](app/backend/src/wastage/wastage.controller.ts) | أي مستخدم مصادق يسرد/ينشئ إتلاف |
| مسار `/accounting/accounts` مكرّر بحارسين متناقضين | account.controller.ts مقابل accounting.controller.ts | هشّ — قد ينقلب لكشف CRUD الشجرة |

### تناقض في الـ seed نفسه
المحاسب مُنح `debts.view/collect` و`wastage.*` بينما صفحات `debts`/`wastage` معلّمة `isAdminOnly:true` ومستبعدة من مفاتيح المحاسب ⟵ عدم اتساق داخلي.

### التوصيات (بانتظار قرارك)
1. إضافة `PermissionsGuard` حقيقي يقرأ `user.permissions`، أو على الأقل `@UseGuards(RolesGuard)` للكنترولرات التي تضع `@Roles` بلا حارس.
2. تقييد الخصم بالإجمالي الفعلي (amount + per-line + pct) من إعداد `pos.accountant_max_discount_pct`.
3. تحويل شطب الديون إلى `@Roles('admin')`.
4. حماية نقاط النهاية المالية والإتلاف.
5. حسم: هل للمحاسب صلاحيات محاسبية أصلاً؟ (الاسم "محاسب" يملك صلاحيات محاسبية أقل في الـ seed مما يمنحه الكود فعلاً — تناقض يحتاج قراراً منك).
